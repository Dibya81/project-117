# ADR 0003 - Phase 0.5 foundation hardening

- Status: accepted
- Date: 2026-09-09
- Phase: 0.5 (runs before Phase 6 Orchestrator)
- Governing principle: security, sandboxing, verification and artifact
  integrity are part of the product, not a later phase.

## Context

The Phase 0 audit found that Phases 1-4 were real - the API, model gateway,
localGPT ingestion and hybrid retrieval genuinely work - but that four
foundation defects were load-bearing enough to fix before building the
orchestrator on top of them.

The review then reordered the plan so security arrives with each phase rather
than after the demo:

```
0.5 hardening -> 6 orchestrator -> 8 tool registry -> 9 sandbox+egress
  -> 11a verification -> 10 deliverables (+11b artifact checks)
  -> 7 agents -> 12 security completion -> 19 demo
```

Phase 0.5 is the first consequence of that reordering: fix the foundation,
then build.

## Decisions

### 1. Egress is enforced, not documented

`EgressPolicy` existed and its unit tests passed, but grep showed it was
referenced in exactly four places: the settings object, the app factory, its
own module and its own test. **No HTTP client ever consulted it.** Every
outbound request went straight out. The zero-egress guarantee was a comment.

Enforcement now lives in an `httpx` transport (`EgressGuardTransport`) rather
than in a helper function that call sites must remember to call. The check sits
*underneath* the client, so it covers chat, embeddings, model listing,
streaming responses and redirects, and a new call site cannot opt out by
forgetting something.

- `OpenAICompatibleProvider` accepts an `egress` policy and wraps its
  transport; `create_app` always supplies it.
- A refused request raises `EgressBlocked`, which providers translate to
  `ProviderEgressBlocked` (`code="egress_blocked"`). This is deliberately
  distinct from `ProviderUnreachable`: the network was never touched, and
  reporting a sovereignty violation as "the backend is down" would hide it.
- `guarded_async_client()` is the sanctioned constructor for future outbound
  clients (Phase 9 sandbox adapter, Phase 13 connectors).
- New setting `P117_EGRESS_ALLOWED_HOSTS`: exact hostnames, no wildcards. A
  wildcard allowlist is how zero-egress quietly becomes full egress.
- `0.0.0.0` was removed from the always-allowed loopback set. It is a bind
  address, not a destination; a base URL pointing there should fail visibly.
- Blocked requests log the host and scheme only. A URL can carry a query, and
  a query can carry document content - that must never reach a log file.

Scope, stated honestly: this covers HTTP made by our own process through httpx.
Vendored code that opens its own sockets (localGPT's embedder, LightRAG's
`pipmaster` install-on-import) is not covered and cannot be from inside this
process. Container-level egress control is Phase 9 and Phase 12 work. This is
the first gate, not the only one.

### 2. Model configuration fails closed

The code defaulted to `qwen3.5:9b`, `qwen3.5:4b` and `Qwen/Qwen3-Reranker-4B`
while `.env.example` implied an unconfigured state. That divergence was a live
bug: a fresh checkout could try to pull multi-GB weights from Hugging Face on
the first request, from a system whose entire pitch is that nothing leaves the
machine.

The rule adopted:

```
no model configured -> download NOTHING -> return a clear configuration error
```

- All six role defaults are now empty. `ModelRouter.resolve` already produced a
  precise error for an unconfigured role ("set P117_REASONING_MODEL"); it is
  now reachable instead of being masked by a default.
- Any role value containing `/` is **rejected at startup**. An Ollama tag is
  `name:tag`; a Hugging Face repo id is `org/name`. The distinction is crude,
  but it is exactly the one that matters for an air-gapped install, and failing
  at boot beats failing halfway through a user's request.
- `P117_ALLOW_REMOTE_MODEL_REPOS=false` is the deliberate escape hatch for
  machines that are intentionally not air-gapped.
- Reranking now defaults to **off** (`retrieval_rerank_enabled=False`), and the
  reranker dependency stack (torch, transformers, accelerate, rerankers) moved
  to an opt-in `rerank` extra. Every reranker backend we vendor resolves to an
  HF download, so shipping it on by default contradicted the posture.

### 3. Audit rows can record provenance

`AuditEvent` could not record an agent, a tool, a model or an approval. That
makes the Phase 7 approval gates unauditable before they are written, so the
columns land now: `agent`, `tool`, `model`, `approval`.

`approval` defaults to `not_required` rather than `approved`. Defaulting to
`approved` would forge consent that nobody gave. Allowed values are a closed
set (`not_required`, `pending`, `approved`, `rejected`) validated in
`AuditService.record`, so a typo cannot silently record an operation as
authorised. `GET /api/audit` can filter by `agent`, `tool` and `approval`,
which is what "show me everything awaiting approval" needs.

### 4. Declared dependencies match imported ones

`python-dotenv`, `numpy` and `pyarrow` are used but were never declared - they
happened to arrive as transitive dependencies of something else. They are now
explicit, so `uv sync` is reproducible rather than lucky.

### 5. Dead code removed

`backend/backend/graph/__init__data.py` declared typed graph errors in a
misnamed file inside a directory with no `__init__.py`. It was never
importable. Phase 5 will reintroduce these errors in a real package when graph
memory actually lands. `ToolOrchestra-main/` is removed per ADR 0002.

## Schema migration note

`init_db` calls `create_all`, which creates missing *tables* but never alters
existing ones. The new `audit_events` columns will therefore be absent from any
SQLite file created before this change, and queries will fail with "no such
column". Until Alembic lands (Phase 17): delete `data/project117.db`, or add
the columns by hand.

## Verification

Phase 0.5 is not complete until this passes on the development machine:

```bash
cd backend
uv sync
uv run pytest -q
uv run ruff check backend tests
uv run pyright backend
```

Three test modules were added: `tests/test_egress_enforcement.py`,
`tests/test_model_config.py`, `tests/test_audit_provenance.py`. The first
includes the specific regression the audit found - that the running app's model
client really does have the guard installed, not merely that a policy object
exists somewhere.

## Consequences

- A deployment that previously "worked" by silently downloading weights will
  now refuse to start, or return a configuration error naming the exact
  environment variable to set. This is the intended behaviour change and the
  most likely source of surprise after applying the patch.
- Retrieval quality drops slightly where reranking was implicitly enabled.
  Re-enable it explicitly with local weights: `uv sync --extra rerank`.
- Phase 9 inherits a working enforcement point instead of having to retrofit
  one underneath a finished system.
